1. Executive summary & feature overview

Hakara combines karaoke recording and editing with a social feed, duets, profiles, and virtual gifts. The main screen launched offline, but the full karaoke and purchase flows were not tested.

3. Source code & policy compliance audit

Priorities reflect potential impact and the strength of the local evidence. These are engineering findings and policy review questions, not legal or store-policy determinations.

FindingEvidence → potential impactRecommended action
F-01 · High
Shared authentication client and HTTP autocomplete		The search UI's suggestions flow is wired through a repository to the absolute HTTP autocomplete URL in ApiService. NetworkModule2 attaches the header interceptor, which adds an identifier and any stored bearer token without a host check. This creates a path for cleartext third-party disclosure of search text and first-party headers when suggestions run. No real token, capture, or transfer was observed.Use a separate unauthenticated HTTPS client for suggestions; restrict credentials and identifiers to the exact first-party HTTPS origin. Remove cleartext exceptions that are not required. Add automated header-isolation tests with synthetic values.
F-02 · High
Account token in reporting URL		Profile report action reads the same stored access_token used for API authorization and embeds it in a query string. HTTPS does not keep URLs out of server logs; history, diagnostics and onward disclosure depend on configuration.Keep bearer tokens out of URLs. Use authenticated in-app submission or a narrowly scoped, short-lived exchange; review log retention and rotate affected tokens if exposure is confirmed.
F-03 · Medium
Embedded browsing and diagnostics		WebViewActivity enables JavaScript and loads an intent URL; the modern navigation handler shows no explicit scheme/host allowlist. Manifest declares no external intent filter for this activity; external reachability was not established. The shared API client installs Stetho and a logging interceptor; no live inspector or credential logging was demonstrated.Allowlist trusted HTTPS destinations, disable JavaScript unless needed, and strip inspection tooling from release builds. Review diagnostic redaction.
F-04 · Medium
Backup, permissions and file sharing		Manifest enables backup and declares microphone, camera, precise/coarse location, and legacy external storage. Access token is read from private SharedPreferences. FileProvider paths include cache and external-storage roots; the provider is not exported and requires a URI grant. No unauthorized backup or file read was tested.Explicitly exclude session and sensitive media from backup, narrow shareable paths, adopt scoped storage, and verify just-in-time permissions and data minimization for location and media.
F-05 · Review required
Consent, user-generated content and rights		Privacy/terms links, report/block actions and recording visibility labels exist. Analytics, crash reporting, ads, media upload and nearby content warrant a data inventory. Account-deletion and moderation enforcement were not verified. YouTube extraction-related paths and bundled native media components warrant terms and licensing review; strings are not proof of infringement.Compare actual collection with disclosures and consent, verify account deletion and report/block handling, and document rights for music, user uploads, YouTube use, and native library redistribution.
F-06 · Review required
Legacy release dependencies		Target SDK 30 and Play Billing Client 3.0.3 are recorded in the sample. Shared request-signing material is supplied by a native library; it should not be relied on as proof that a request comes from a trusted client. No key value was collected for this report.Check current Play submission requirements for the intended release channel; update SDKs, inventory native dependencies, and enforce identity and authorization server-side.

Evidence and next steps

Sample SHA-256: 9DA68EA4F50B7228155C95C29A9C16CDA8AB623F19F99440DD513AB759D451AF (recorded in the recovery review). Offline scope · Recovery and emulator results · Case timeline.

  1. Before any authenticated test: Fix F-01 and F-02. In local tests with synthetic data, confirm that autocomplete sends no first-party credentials or device identifiers, and that report URLs contain no account token.
  2. Before signing off on features: With separate authorization for online testing, verify sign-in, song search and playback, solo/duet recording, export, upload visibility, and moderation. Use test accounts and non-sensitive media; compare against an authentic install where available.
  3. Before claiming monetization works: Use test ads and Play's testing environment to verify reward delivery, purchase, cancellation and entitlement. Confirm active products and revenue streams with console records.
  4. Before publishing release changes: Obtain an authentic previous APK or source tag. Compare resource paths and hashes, inspect changed icons, and trace changed assets to the UI that uses them.

Obfuscation, JADX reconstruction errors, absent backend/native source, and offline-only evidence limit conclusions. Neither a matching export count nor a successful smoke test establishes full behavioral equivalence.
